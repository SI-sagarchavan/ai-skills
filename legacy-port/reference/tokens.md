# Tailwind and the token system

Surface plugins are styled with Tailwind plus the tenant's design tokens. The
token utilities are **not** Tailwind classes, and that decides most of what
follows.

## Where token classes come from

- On every page render the renderer builds one stylesheet from the tenant
  theme. The theme is master-layouts `tokens[<page schema theme.main_theme>]`.
  The stylesheet is generated by `genCssFromJson` in
  `packages/utils/src/lib/theme-generator/cssFromJson/` and inlined into the
  page.
- It declares the variables on `:root`:
  - `--<token>: H S% L%`, meant for `hsl()`;
  - `--<token>-hex`;
  - spacing, radius, opacity, gradient and typography variables.
- It generates the utilities for **every** token in the theme, whether used
  or not.
- It generates **no** `hover:`, `focus:`, `md:` or other variants of those
  utilities. `hover:text-text_main_high` and `md:p-spacing_4` have no CSS
  behind them.
- `apps/web/theme.json` is a sample theme. It is the list of existing token
  names, not a tenant's values.

## Token utilities

| Family | Utilities | Notes |
|---|---|---|
| Colour (`core_prim_*`, `core_sec_*`, `core_neu_*`, `text_*`, `background_*`, `border_*`, `color_*`) | `text-<t>`, `bg-<t>`, `border-<t>` | value `hsl(var(--<t>))` |
| Spacing (`spacing_0` … `spacing_N`, px) | `p-`, `px-`, `py-`, `pt-`, `pr-`, `pb-`, `pl-`, `gap-`, `gap-x-`, `gap-y-` + `spacing_N` | no margin, no width/height |
| Radius (`radius_xs` … `radius_3xl`, `radius_none`) | `rounded-tl-`, `-tr-`, `-bl-`, `-br-<t>` | per corner only; there is no `rounded-<t>` |
| Typography (`h1_bold`, `body_sm_medium`, `button_lg` …) | bare class `.<t>` (+ `.line-clamp-1..5`) | size, line height, weight, family; **re-scales itself at 768px and 1200px** |
| Shadow (`shadow_sm` … `shadow_xl`) | bare class `.<t>` | |
| Gradient | `bg-gradient-<t>` | |

## Writing the classes

- **Colours.** Use the token class: `text-text_main_high`, `bg-core_neu_00`,
  `border-border_main_default`.
  - For a variant, use an arbitrary value on the variable:
    `hover:text-[hsl(var(--text_prim_high))]`,
    `md:bg-[hsl(var(--background_main_card))]`. Those are real Tailwind
    classes, so the variants work.
  - Alpha: `bg-[hsl(var(--core_neu_950)/0.5)]`. The `/50` modifier does not
    exist on token classes.
  - Transparent: `bg-transparent`.
- **Spacing.**
  - Padding and gap: `p-spacing_N` when `tokens.mjs` matched a token.
  - Margin, width and height, or a value with no token: Tailwind's scale.
    v4 takes any quarter step, so 10px is `p-2.5` and 15px is `mt-3.75`.
  - Responsive: `md:p-[var(--spacing_4)]`, or the Tailwind scale.
- **Type.** Prefer a typography class (`h3_bold`) when `tokens.mjs` lists one
  for the size. It already changes size at 768/1200, so don't add
  `md:h1_bold`, which has no rule.
  - When the legacy breakpoints differ from 768/1200, or no typography token
    fits, use Tailwind `text-[length:…]`/`leading-*`/`font-*` with
    arbitrary breakpoints.
- **Radius.** `rounded-tl-radius_sm rounded-tr-radius_sm …` per corner, or
  Tailwind `rounded-[3px]` when there is no token.
- **Breakpoints.** The legacy CSS uses 768/992/1200. Tailwind's are
  640/768/1024/1280/1536.
  - `md:` matches 768.
  - For the others use arbitrary breakpoints: `min-[992px]:`, `min-[1200px]:`,
    `max-[767px]:`. Copy the legacy media queries; don't round them to
    Tailwind's.
- **Fonts.** The family comes from the typography token, and the tenant's
  Font Manager fonts are already on every page. Use the tenant's families and
  its icon font as `tokens.mjs` maps them; do not use the legacy site's font
  files or icon font. For a breakpoint on a typography token see
  [porting-rules.md](porting-rules.md) (Typography tokens in practice).
- **Never** add a tenant class, colour or font to the renderer, and never add
  a global stylesheet. A plugin may ship a small `ui/Component.css` for what
  Tailwind cannot express, such as complex `::before` content or keyframes.
  Use token variables in it, never raw values.

## When the tenant theme is empty or incomplete

New tenants often start with an empty theme (PBKS had no colour, spacing or
typography values). The port then fills it:

1. In `tokens.json`, read each legacy colour's uses (text, background,
   border) and its legacy variable name (`--primary-color`). Those two tell
   you its role.
2. Assign it to an **existing** token name with the same role:
   - text colours → `text_main_*` / `text_prim_*` / `text_invert_*`;
   - surfaces → `background_*`;
   - lines → `border_main_*`;
   - brand ramps → `core_prim_*` / `core_sec_*`.
3. Put the assignments in `legacy-port.json`:

   ```json
   "theme": {
     "proposed": {
       "color": { "light": { "core_prim_500": "#ed1c24", "text_main_high": "#000000" } },
       "spacing": { "spacing_2_5": 10 },
       "typography_desktop": { "h4_bold": { "name": "h4_bold", "size": 20, "weight": 700, "typeface": "acuminpro-bold", "line_height": 24, "letter_spacing": 0 } }
     }
   }
   ```

4. Re-run `tokens.mjs`. It rejects names that are not existing tokens, and
   builds `theme.css` (tenant theme + proposal) for the comparison.
5. Show the user the "to set in the tenant theme" list. Those values must be
   set on the tenant's theme in admin before the page is published,
   otherwise the plugin renders with empty colours.
6. A proposal for a token the tenant already has overrides it in
   `theme.css`, and `tokens.mjs` prints it under "CHANGES existing tenant
   values". Avoid that. If it cannot be avoided, tell the user, because it
   changes every page of the tenant.
